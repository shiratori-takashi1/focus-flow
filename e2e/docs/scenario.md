# E2Eテストシナリオ記述仕様書

本ドキュメントは、プロジェクトにおけるAI駆動型E2Eテストのための「自然言語シナリオ」の記述フォーマット、命名規則、およびディレクトリ構造の仕様を定義するものです。

本仕様は、**人間にとっての直感的な仕様書**であると同時に、**AIエージェント（Cursor, Claude Code, Browser Use等）が最も高精度にコード生成・自律実行できる指示書**として最適化されています。

## 1. シナリオの記述フォーマット (Template Format)

すべてのシナリオは以下のMarkdownフォーマットに従って記述します。
システム的な識別は `メタ情報` の `id`（ファイル名と同期）に任せるため、大見出し（`# 機能`）は「【機能名】 誰が・どうして・どうなるか（ユーザーの目的・ストーリー）」という純粋な日本語のストーリーで記述します。

### テンプレート

```md
# 機能

[[機能名]] [誰が] [どんな操作をして] [どうなるか（ユーザーの目的・ストーリー）]
## メタ情報
- id: [格納フォルダ名なしのファイル名（例: login__failure-invalid-password）]
- tags: [カンマ区切りのタグ（例: auth, shelf-layout, customtag）]
- related_pages: [[関連するパスの配列（例: [/login, /service/notification/, /service/notification/create/]）]]

## 前提条件
- [テスト実行前に満たされているべき前提条件を箇条書きで記述]
- [例：テスト用ユーザー（test@example.com）がシステム内に存在すること]
- [例：ユーザーは未ログイン状態であること]

## 操作手順

### 1. [ステップの見出し（例：ログインページを開く）]
- [具体的案操作内容を自然言語で記述。URLや遷移先を明示する]
- [例：ログイン画面（`/login`）に直接アクセスする。]

### 2. [ステップの見出し（例：誤ったログイン情報を入力する）]
- [AIが画面上の要素を迷わず特定できるよう、ラベルやプレースホルダーの特徴を記載する]
- [例：「メールアドレス」の入力欄に `test@example.com` と入力する。]
- [例：パスワード入力欄に、間違ったパスワード（例: `wrong_password`）を入力する。]

### 3. [ステップの見出し（例：ログインを実行する）]
- [例：フォーム内にある「ログイン」と書かれたボタンをクリックする。]

## 検証内容
- [テストが「成功」と判定されるための期待される結果・ゴールを明記する]
- [例：画面遷移せず、ログインページ（`/login`）にとどまっていること。]
- [例：画面内に「メールアドレスまたはパスワードが間違っています」というエラーメッセージが表示されていること。]

```

## 2. ファイル命名規則 (Naming Convention)

ファイル名はすべて**小文字の英数字**とし、大分類（機能名）と、小分類（結果・状態・ケース）を明確に分離するために **`__`（ダブルアンダースコア）** と **`-`（ハイフン）** を使い分けます。また、このファイル名は上記フォーマットの `メタ情報` 内の `id` と完全に同期させます。

```text
[機能名] __ [結果・状態] - [詳細なケース].md

```

### 命名の構成要素

1. **`機能名`**: テスト対象の最小の機能単位・ドメイン（例: `login`, `cart`, `checkout`）
2. **`__`（ダブルアンダースコア）**: 機能名と、テスト結果・状態の「文脈の切り替え」を明示する境界線
3. **`結果・状態`**: 成功（`success`）か、失敗（`failure`）か、あるいは特定の状態（例: `pending`）か
4. **`-`（ハイフン）**: その状態を引き起こす具体的なケースのバリエーション

### 具体例

* `login__success.md` （※単一の成功ルートの場合は詳細ケースを省略してシンプルにする）
* `login__failure-invalid-password.md`
* `login__failure-locked-account.md`

## 3. ファイル配置とディレクトリ構造 (Directory Structure)

作成したシナリオファイルは `e2e/scenarios/` 配下に格納し、**必ずドメイン（機能・コンポーネント）ごとのディレクトリに分類**します。実際のPlaywright等のテストコード（`e2e/specs/`）と1対1でシンクロする構造を維持してください。

```text
e2e/                            # ★E2Eテストに関する資産をすべて集約
├── scenarios/                  # ★自然言語によるシナリオ (.md)
│   ├── _shared/                # 🌟【新設】共通のパーツ・シナリオ部品
│   │   ├── login.md            # 例：ユーザーでのログイン手順
│   │   └── move-to-notice-list-page.md      # 例：お知らせの一覧画面移動する手順
│   ├── auth/
│   │   ├── login__success.md
│   │   └── login__failure-invalid-password.md
│   ├── cart/
│   └── checkout/
│
└── specs/                      # ★実際のテストコード (.spec.ts)
    ├── _shared/                # 🌟【新設】Playwright側の共通関数・Page Object
    │   ├── login.ts            # シナリオの login.md と1対1で対応
    │   └── move-to-notice-list-page.ts       # シナリオの move-to-notice-list-page.md と1対1で対応
    ├── auth/
    │   ├── login__success.spec.ts
    │   └── login__failure-invalid-password.spec.ts
    ├── cart/
    └── checkout/

```

## 4. 記述の作法と役割分担 (Best Practices)

### ① システム識別（メタ情報 id）と人間用見出し（機能）の役割分担

* **`メタ情報` の `id**` はファイル名と完全に一致させます。これにより、AI（Cursor/Claude）やプログラムが「どのテストコード（`.spec.ts`）と紐付いているか」を機械的に100%特定できます。
* **`# 機能`** は人間（開発者、PM、QA）がパッと見て直感的に理解できる仕様の要約です。具体的なストーリー（目的）が書かれていることで、AIも「テストの本当に担保すべき重心」を深く理解し、手厚い検証コードを出力してくれます。

### ② AIの迷子を防ぐ「見通し（related_pages）」

* Browser UseやComputer UseのようなAIエージェントに自律実行させる際、遷移する可能性のあるURL（`related_pages`）があらかじめ明記されていることで、AIの推論精度が劇的に向上し、実行が安定します。

### ③ 要素の特定は「抽象」ではなく「具体的」にする

* ❌ **悪い例:** `ターゲット: ログインボタン` (AIが画面内の他のボタンと誤認するリスクがある)
* ⭕ **良い例:** `フォーム内にある「ログイン」と書かれたボタンをクリックする` (AIが文脈やテキストから正確に特定できる)

### ④ 仕様とテストコードの「同時更新」をAIに命令する

本ファイルをGit管理に含めることで、フロントエンドのコード（`src/` 配下）を変更した際、CursorのComposerやClaude Codeに対して以下のようなプロンプトを実行するだけで、**仕様書（Markdown）とテストコード（TypeScript）の双方を完璧に同期して自動修正**させることが可能になります。

> 💬 **AIへの指示例：**
> 「`src/components/LoginForm.tsx` のバリデーション文言を修正した。これに合わせて、`e2e/scenarios/auth/` にある関連シナリオと、`e2e/specs/auth/` にあるPlaywrightのテストコードを両方とも自動で最新の仕様にアップデートして」

本仕様はプロジェクトの規模や使用するAIツールの進化に合わせて、適宜チーム内でレビューしアップデートを行います。

## 5. 共通ファイルの記述フォーマット（テンプレート）

```md
# 共通手順: [部品の名前（例：運営ユーザーでのログイン）]

## 概要
- [この共通パーツが何をするためのものか、一言で記述]
- [例：運営管理画面（/admin）へログインするための共通手順。]

## 処理手順

### 1. [ステップの見出し（例：ログイン画面を開く）]
- [具体的な操作内容を自然言語で記述]
- [例：運営ログイン画面（`/admin/login`）に直接アクセスする。]

### 2. [ステップの見出し（例：認証情報を入力して実行する）]
- [例：「管理者ID」の入力欄に環境変数またはテスト用のアカウントIDを入力する。]
- [例：パスワード入力欄にパスワードを入力し、「ログイン」ボタンをクリックする。]


```

### このフォーマットにする際の3つのポイント

#### 1. タイトルを「# 共通手順: 〜」にする

大見出しを `# 機能` ではなく `# 共通手順:` で始めることで、人間が見たときにも、AIがファイル群をスキャンしたときにも、「これは単体で走るテストケースではなく、ただの部品（関数）だな」と一発で判別できるようになります。

#### 2. 「検証内容（Assertions）」は原則書かない

共通手順の目的は「状態を作ること（例：ログイン状態にする、カートに商品が入った状態にする）」です。そのため、基本的には手順だけを書きます。
どうしても「ログインに成功してダッシュボードが表示されていること」を担保したい場合は、手順の最後に `- ダッシュボード画面（`/admin/dashboard`）が表示されたことを確認する。` のように、手順の中の1ステップとしてチェック項目を滑り込ませるのが綺麗です。

#### 3. 動的な値（変数）を使いたい場合の書き方

例えば、「カートに商品を入れる」という共通手順で、「商品Aを入れる場合もあれば、商品Bを入れる場合もある」というように、呼び出し元によって値を変えたい（引数を持たせたい）場合があります。

その場合は、以下のように**引数（パラメーター）の受け皿**を作っておくと、AIがPlaywrightのコード側で「引数を持つ共通関数」を正しく定義してくれます。

#### 💡 引数を持たせる場合の共通ファイル記述例：

```md
# 共通手順: 商品をカートに追加する

## 概要
- 指定された商品を詳細画面からカートに追加する。

## 引数（パラメーター）
- `商品名`: 呼び出し元で指定された商品の名前

## 処理手順

### 1. 商品詳細ページを開く
- `/products` の一覧から、指定された `商品名` のリンクをクリックする。

### 2. カートに追加する
- 画面内にある「カートに入れる」ボタンをクリックする。

```

このように書いておけば、呼び出し側のシナリオで `[../_shared/add_to_cart.md](商品名="特製ネコ缶") の手順を実行する` と指示するだけで、AIが意図を組んで動的な共通関数を裏側で組み立ててくれるようになります。
